## 4. 现在平台的核心工作流是什么

你可以先把 LuckyModels 理解成两部分：

- 控制平面：负责“看见模型、登记模型、创建部署、记录状态”
- 运行时平面：负责“真正加载模型并提供推理接口”

当前工作流是这样的：

1. 模型包放到 `artifacts/models/...`
2. 每个模型包必须带 `manifest.yaml`
3. 控制平面扫描 `artifacts/models/`
4. 扫描到模型后，对外暴露模型列表、模型详情、Profile 列表
5. 创建部署时，控制平面先生成一条部署记录
6. 运行时服务通过 `manifest + profile` 加载指定模型包
7. 运行时统一暴露 `/healthz`、`/metadata`、`/predict`、`/metrics`

## 7. 为什么 CasRel 还没有完整推理

因为 CasRel 不是一个简单的单 ONNX 模型。

你现在的制品里至少包含：

- `casrel_subject.onnx`
- `casrel_object.onnx`
- `vocab.txt`
- `rel2id.json`

这说明它的推理真实链路一定是：

- tokenizer 预处理
- subject 模型推理
- object 模型推理
- 三元组解码

所以我这次先把“包规范、服务接口、加载骨架”搭好，而没有假装把推理乱写完。这样比给你一版不可信的假实现更稳。

## 10. 如果你问“现在最核心的设计思想是什么”

一句话就是：

**LuckyModels 不直接理解每个模型的内部推理细节，而是通过标准模型包 + Adapter + Profile，把不同知识抽取模型统一纳入一个平台。**

这也是你后面论文和系统实现最应该保持一致的主线。
