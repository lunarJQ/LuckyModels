## 4. 现在平台的核心工作流是什么

你可以先把 LuckyModels 理解成两部分：

- 控制平面：负责“看见模型、登记模型、创建部署、记录状态”
- 运行时平面：负责“真正加载模型并提供推理接口”

当前工作流是这样的：

1. 模型包放到 `artifacts/models/...`
2. 每个模型包必须带 `manifest.yaml`
3. 控制平面扫描 `artifacts/models/`
4. 扫描到模型后，对外暴露模型列表、模型详情、Profile 列表
5. 创建 deployment 时，控制平面先生成一条部署记录
6. 如果设置 `launch_runtime=true`，控制平面会自动分配一个空闲本地端口并拉起 runtime
7. 运行时服务通过 `manifest + profile` 加载指定模型包
8. 运行时统一暴露 `/healthz`、`/metadata`、`/predict`、`/metrics`
9. benchmark 模块可以对某个 deployment 发起多轮请求，记录平均延迟、P95 和吞吐

## 7. 为什么 CasRel 还需要继续调优

因为 CasRel 不是一个简单的单 ONNX 模型。

你现在的制品里至少包含：

- `casrel_subject.onnx`
- `casrel_object.onnx`
- `vocab.txt`
- `rel2id.json`

这说明它的推理真实链路一定是：

- tokenizer 预处理
- subject 模型推理
- object 模型推理
- 三元组解码

现在 LuckyModels 已经把这条链路真正接起来了，但当前样例输入还容易出现 `triple_count = 0` 的结果。
这更像是“模型制品和当前预处理假设之间还要继续校准”，而不是平台根本跑不起来。

## 11. 如果你问“现在最核心的设计思想是什么”

一句话就是：

**LuckyModels 不直接理解每个模型的内部推理细节，而是通过标准模型包 + Adapter + Profile，把不同知识抽取模型统一纳入一个平台。**

这也是你后面论文和系统实现最应该保持一致的主线。

## 12. 如果后面要用 Docker，怎么保证不影响别人

我的建议很明确：

- LuckyModels 只用自己独立的 compose 文件
- host 端口统一用高位端口，不抢常见的 `8080`、`9090`
- compose 启动时带独立 project name，比如 `luckymodels-local`
- 不去改别人已经在跑的容器名、网络、卷

现在仓库里的 `infra/compose/docker-compose.local.yml` 也已经按这个方向收敛了，后面如果你要我继续把 API、Prometheus、Grafana 做成一套独立的本地 Docker 栈，我就沿着这个约束继续做。
