## 2.1 当前这套“在线学习 + 部署策略”怎么理解

可以把当前平台里的三条增强算法理解成：

1. 无用户反馈下的任务调度校准
   主要读取 benchmark 与 prediction archive，不要求用户显式点满意/不满意。
2. 用户反馈驱动的任务调度校准
   读取任务调度反馈和结果反馈，显式修正各目标权重。
3. 跨层协同部署策略
   把模型热度、benchmark、任务调度价值、自动重启/CPU 回退历史、GPU 池可用性放在一起，输出部署建议。

这三条链路现在都不是“只在论文里写一写”，而是已经有真实接口和真实状态数据。

## 4. 现在平台的核心工作流是什么

你可以先把 LuckyModels 理解成两部分：

- 控制平面：负责“看见模型、登记模型、创建部署、记录状态”
- 运行时平面：负责“真正加载模型并提供推理接口”

当前工作流是这样的：

1. 模型包放到 `artifacts/models/...`
2. 每个模型包必须带 `manifest.yaml`
3. 控制平面扫描 `artifacts/models/`
4. 扫描到模型后，对外暴露模型列表、模型详情、Profile 列表
5. 创建 deployment 时，控制平面先生成一条部署记录
6. 如果设置 `launch_runtime=true`，控制平面会自动分配一个空闲本地端口并拉起 runtime
7. 运行时服务通过 `manifest + profile` 加载指定模型包
8. 运行时统一暴露 `/healthz`、`/metadata`、`/predict`、`/metrics`
9. benchmark 模块可以对某个 deployment 发起多轮请求，记录平均延迟、P95 和吞吐
10. task routing 可以按目标、场景和模型种类筛选当前候选 deployment
11. 调度结果会落成 `pred-*` 预测归档和 `trd-*` 决策记录
12. 结果反馈会反向作用到任务调度在线学习

## 4.1 benchmark 现在怎么参与任务调度学习

这一点专门写清楚，避免后面再混淆。

当前任务调度不是把所有 benchmark 历史记录都直接累加进去，而是：

- 先按 `benchmark_scope_key` 分组
- 每组优先取 `is_effective=true` 的最新一条
- 如果这组没有 effective 记录，再退回到该组最新记录

也就是说，任务调度学习的是“最新有效 benchmark”，旧 benchmark 会保留在平台里用于追踪和论文展示，但不会被重复算进当前权重学习。

## 7. 为什么 CasRel 还需要继续调优

因为 CasRel 不是一个简单的单 ONNX 模型。

你现在的制品里至少包含：

- `casrel_subject.onnx`
- `casrel_object.onnx`
- `vocab.txt`
- `rel2id.json`

这说明它的推理真实链路一定是：

- tokenizer 预处理
- subject 模型推理
- object 模型推理
- 三元组解码

现在 LuckyModels 已经把这条链路真正接起来了，但当前样例输入还容易出现 `triple_count = 0` 的结果。
这更像是“模型制品和当前预处理假设之间还要继续校准”，而不是平台根本跑不起来。

## 11. Profile 现在已经不是摆设了

这一点对你论文里的“部署优化”特别重要，我单独说清楚。

现在 LuckyModels 里的 `profile.yaml` 已经真正接到了 runtime：

- `execution.instance_count`
  控制 runtime 启动时 `uvicorn --workers N`
- `execution.intra_op_threads`
  控制 ONNX Runtime 的 `intra_op_num_threads`
- `execution.inter_op_threads`
  控制 ONNX Runtime 的 `inter_op_num_threads`
- `execution.batch_size`
  控制 benchmark 的批量请求规模，也支持 runtime 通过 `texts` 走批量预测

这意味着你现在已经可以围绕同一个模型写出几套真实可对比的 profile：

- `latency`
  小 batch、较少 worker、偏低排队延迟
- `balanced`
  中等 batch、中等 worker、作为默认论文对照组
- `throughput`
  更大的 batch、更多 worker，用来换吞吐
- `memory`
  保守线程数和实例数，优先压资源占用

平台层面也已经开始把这部分信息展示出来：

- 部署记录页会显示 profile、device、workers、batch_size、线程参数
- 运行资源页会展示运行中 deployment 的 runtime 快照
- benchmark 统计中的 `total_requests` 和 `throughput_qps` 已按 batch 后的真实 item 数计算

有一个使用上的注意点：

- 如果某个 deployment 是在 2026-03-28 这次更新之前创建并一直没有重启，它还在跑旧进程
- 这类 deployment 需要执行一次“重启”，新的 profile 参数才会生效

## 12. 如果你问“现在最核心的设计思想是什么”

一句话就是：

**LuckyModels 不直接理解每个模型的内部推理细节，而是通过标准模型包 + Adapter + Profile，把不同知识抽取模型统一纳入一个平台。**

这也是你后面论文和系统实现最应该保持一致的主线。

## 13. 如果后面要用 Docker，怎么保证不影响别人

我的建议很明确：

- LuckyModels 只用自己独立的 compose 文件
- host 端口统一用高位端口，不抢常见的 `8080`、`9090`
- compose 启动时带独立 project name，比如 `luckymodels-local`
- 不去改别人已经在跑的容器名、网络、卷

现在仓库里的 `infra/compose/docker-compose.local.yml` 也已经按这个方向收敛了，后面如果你要我继续把 API、Prometheus、Grafana 做成一套独立的本地 Docker 栈，我就沿着这个约束继续做。
