# LuckyModels 本地运行与基准测试

这份文档专门回答两个问题：

1. 现在 LuckyModels 怎么在本机上安全跑起来
2. 怎么做一版可以写进论文的基础 benchmark

## 1. 安全原则

为了不影响机器上其他业务，LuckyModels 当前遵循这几个原则：

- 默认只监听 `127.0.0.1`
- 默认使用高位端口
- 控制平面自动拉起 runtime 时，优先动态分配空闲端口
- 不主动停止、重启、删除其他人的 Docker 容器

## 2. 启动控制平面

```bash
cd /home/liujingqian/LuckyModels
/home/liujingqian/LuckyModels/scripts/run_api.sh
```

默认地址：

- `http://127.0.0.1:38080`

如果端口冲突：

- 脚本会自动切换到一个空闲本地端口，不需要你去停别人的服务
- 终端里会打印最终实际使用的端口

如果你想手工指定一个优先端口：

```bash
LUCKYMODELS_API_PORT=38180 /home/liujingqian/LuckyModels/scripts/run_api.sh
```

## 3. 查看平台状态

```bash
curl http://127.0.0.1:38080/healthz
curl http://127.0.0.1:38080/api/v1/system/summary
curl http://127.0.0.1:38080/api/v1/models
```

如果你不想手敲接口，也可以直接跑一个闭环演示脚本：

```bash
cd /home/liujingqian/LuckyModels
.venv/bin/python scripts/demo_local_flow.py
```

这个脚本会自动做这几件事：

- 查看系统摘要
- 列出可用模型
- 创建一个本地 deployment
- 用 WebNLG 英文样本做一次 benchmark
- 把 deployment 停掉

## 4. 创建一个本地部署

推荐直接走控制平面自动拉起 runtime，不要手工固定端口。

```bash
curl -X POST http://127.0.0.1:38080/api/v1/deployments \
  -H 'Content-Type: application/json' \
  -d '{
    "model_id": "casrel-en-webnlg-v1",
    "profile_name": "default",
    "launch_runtime": true
  }'
```

返回结果里最重要的是：

- `deployment_id`
- `service_url`
- `log_path`
- `status`

## 5. 看部署状态和日志

```bash
curl http://127.0.0.1:38080/api/v1/deployments/<deployment_id>/health
curl http://127.0.0.1:38080/api/v1/deployments/<deployment_id>/logs
```

其中：

- `health` 用来看 runtime 是否已真正可访问
- `logs` 用来看启动日志和推理报错

## 6. 跑一版基础 benchmark

对于当前这份 CasRel 制品，优先使用 WebNLG 英文样本，不要再用中文装备句子做性能采样，否则很容易出现空三元组或与模型标签体系不匹配的情况。

你可以先让平台准备一份固定测试样本集：

```bash
curl -X POST 'http://127.0.0.1:38080/api/v1/demo/casrel/prepare-webnlg?limit=128'
```

返回里会包含：

- `dataset_source`
- `record_count`
- `output_path`

当前默认导出的测试集文件是：

- `data/state/reports/webnlg_eval_cases.json`

```bash
curl -X POST http://127.0.0.1:38080/api/v1/benchmarks \
  -H 'Content-Type: application/json' \
  -d '{
    "deployment_id": "<deployment_id>",
    "text": "The ground of A.S. Gubbio 1910 is located in Italy , where the capital is Rome , the leader is Sergio Mattarella and the language spoken is Italian .",
    "iterations": 10,
    "warmup_runs": 1,
    "options": {
      "subject_threshold": 0.0001,
      "object_threshold": 0.0001
    }
  }'
```

当前版本会记录这些结果：

- `avg_latency_ms`
- `p95_latency_ms`
- `throughput_qps`
- `remote_avg_latency_ms`
- `success_count`
- `failure_count`

这些字段已经足够支撑你做论文里的第一轮部署对比。

补充一点：

- 当前 8 个英文模型包都能在平台注册、查询、展示
- 只有 `casrel-en-webnlg-v1` 已经打通了真实在线推理链路
- 其他模型目前属于 `package_ready`，适合先做制品管理、参数展示和后续适配排期

## 7. 这一版 benchmark 能怎么写进论文

你可以先做最简单的三组 profile 对比：

- `latency`
  偏低延迟，适合短文本单条请求
- `balanced`
  平衡型，作为默认部署方案
- `memory`
  偏低资源占用，适合资源紧张场景

然后固定输入文本集合，对不同 profile 记录：

- 平均延迟
- P95 延迟
- 吞吐量
- 成功率

后面如果接入 GPU 指标，再加：

- GPU 显存占用
- GPU 利用率
- CPU 内存占用

## 8. 当前还要保持清醒的地方

目前 CasRel runtime 已经可以真实加载 ONNX 并完成推理请求，但抽取质量还需要继续调优。

也就是说：

- 工程链路基本已经通了
- 性能对比已经可以开始做
- 结果质量这一块还需要继续对 tokenizer、阈值、解码逻辑做校准

当前这个上传包还有一个非常重要的现实情况：

- 关系标签看起来更像 WebNLG 风格英文 schema
- 它更适合被当作 LuckyModels 的运行时兼容性样板
- 不应该把它直接当成最终中文装备制造领域模型

如果你要调质量，建议直接走 debug 预测：

```bash
curl -X POST http://127.0.0.1:<runtime_port>/predict \
  -H 'Content-Type: application/json' \
  -d '{
    "text": "Narendra Modi and Sumitra Mahajan are leaders in India where Amdavad ni Gufa is located in Ahmedabad .",
    "options": {
      "subject_threshold": 0.0001,
      "object_threshold": 0.0001,
      "debug": true
    }
  }'
```

这样返回里会带出：

- `warnings`
- `debug.token_pieces`
- `debug.token_ids`
- `debug.subject_score_summary`
- `debug.subject_candidates`

你后面判断问题是“制品不匹配”还是“阈值不合适”，就主要看这些字段。

## 9. 如果后面要用 Docker

可以用，但要遵守这几个约束：

- 只用 LuckyModels 自己的 compose 文件
- 使用独立 project name
- host 端口继续走高位端口
- 不去改其他容器

建议命令：

```bash
cd /home/liujingqian/LuckyModels
docker compose -p luckymodels-local -f infra/compose/docker-compose.local.yml up -d
```

这样就算这台机器上已经有人在跑别的容器，也不会把他们的容器直接带进 LuckyModels 的编排范围里。
